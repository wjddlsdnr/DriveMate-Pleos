# 피로·졸음·무응답 실제 음성 시험

기준 feature/voice-state / af99833. 기존 정상·로컬 미디어 검증 결과를 유지한다.
차량 제어/경로 변경/긴급 신고는 실행하지 않는다. 원문 없이 메타데이터와 상태만 기록한다.

## 예상 전이와 순서(실행 전 작성)

| 순서 | 입력/상황 | 예상 상태와 대응 |
|---|---|---|
| 1 | 현재 정상 세션에서 가벼운 피로 보고 | CAUTION / MILD_FATIGUE, 휴식 권고, 5분 후속 예약. 실제 차량 포트 미지원 안내 |
| 2 | 같은 세션에서 지속 피로 보고 | WARNING / PERSISTENT_FATIGUE, 일반 콘텐츠 중단, 즉시 휴식 권고, restStopNeeded=true, 1분 후속 예약 |
| 3 | 새 세션에서 정상→로컬 미디어 준비 후 심한 졸음 보고 | HIGH_RISK / SEVERE, 콘텐츠 중단과 즉시 휴식 권고, 검색 필요 판단 |
| 4 | 새 세션에서 정상 확인 후 상태 질문에 침묵 | 실제 SDK 반환형 관찰. Timeout/RecognitionFailure/서비스 오류를 NoResponse나 졸음으로 바꾸지 않음 |
| 자동만 | 명시적인 NoResponse 1회/2회 | 미확인 유지/고위험 의심. 실제 졸음 확정 아님. 시간 초과·권한·서비스 실패는 무응답 횟수에 넣지 않음 |

상태 확인 버튼을 이용한 후속 시험은 수동으로 즉시 실행하며, 실제로 5분/1분을 기다려
자동 스케줄이 실행됐다고 주장하지 않는다. 예약 정책은 가상 시간 테스트로 확인한다.
위험 시험 후에는 음성 연결을 껐다 켜 독립 세션으로 재준비한다.
실제 운전 상태 판단이 아닌 정차된 에뮬레이터에서의 응답 기반 소프트웨어 시험이다.

## 실제 연결 경계

- DriveMateAppGraph realVoice=true의 VehicleController는 propose/apply/restore 모두 UNSUPPORTED.
- ObservedVoiceRoute는 경로 읽기만 허용하며 목적지/경유지/재개 명령은 UNSUPPORTED.
- 실제 휴식 검색은 안전 근거가 연결되지 않아 미지원. 후보를 만들거나 경로를 강제 변경하지 않는다.
- Gleo/외부 콘텐츠/차량 setter/긴급 신고 기능은 이 시험에서 실행하지 않는다.
- PleosRecognitionResult는 빈 최종 결과를 RecognitionFailure로 처리하고, SDK 오류 매핑은
  TIMEOUT→Timeout, MIC/AUDIO 오류→RecognitionFailure, 기타 서비스 실패로 구분한다.
  STT 실패/침묵을 자동으로 NoResponse로 변환하지 않는다.
- 권한/서비스 장애는 실제로 관찰하지 않으면 자동 Fake 결과로만 보고한다.

## 결과

준비 중. 아래 자동 검증과 실제 사용자 발화를 별도 기록한다.

## 자동 검증 및 실제 시험 준비

assembleDebug/testDebugUnitTest에 SafetyResponseCoordinatorTest,
DefaultDriverStateManagerTest, PleosVoiceResultTest, MediaPreemptingVoiceBackendTest만
필터로 지정해 실행했다. BUILD SUCCESSFUL(17초), 테스트 52개/실패 0/오류 0.
이 결과는 Fake·가상 시간·SDK 오류 매핑 검사이며 실제 차량 제어나 실제 무응답 단계 상승이 아니다.
에뮬레이터 화면 캡처 실패 1회 후 창을 다시 선택해 복구했고 실제 음성 켜짐/IDLE,
정상 응답/로컬 재생 중단 상태를 확인했다. 기존 안내 경로는 유지한다.
첫 가벼운 피로 시험의 사용자 준비를 요청했으며 아직 해당 청취는 시작하지 않았다.

## 가벼운 피로 실제 시험

첫 시도는 TTS_DONE→STT_REQUESTED/READY 뒤 발화 시작/최종 콜백이 없었고
약 10초 청취 제한 후 STT_RELEASED/미확인 안내였다. 사용자는 발화했다고 확인했다.
타이밍/입력 실패 원인은 확정하지 않는다. 이 시도는 의도적인 침묵 시험이 아니며
졸음 또는 명시적 NoResponse 성공으로 기록하지 않는다.

재시험에서 실제 STT_FINAL(length=6)/RELEASED 후 condition=MILD_FATIGUE를 수신했다.
화면은 ‘주의 · 피로 응답’(CAUTION)으로 전환됐다. 후속 안내 TTS_DONE을 두 차례 확인했다.
코드상 해당 안내는 휴식 권고와 UNSUPPORTED 차량 보조 안내이며 화면에도 지원되지 않는 기능이 표시됐다.
환기 제안 포트는 미지원이므로 실제 apply/restore/차량 SDK setter는 호출하지 않았다.
사용자에게 안내 청취 여부와 다음 지속 피로 시험 준비를 요청했다.
5분 후속 자동 실행은 이 시도에서 기다려 관찰한 것이 아니며 예약은 자동 테스트로 구분한다.

## 지속 피로 실제 시험

사용자는 앞선 휴식 권고와 환기 보조 미지원 안내를 들었다고 확인했다.
같은 CAUTION 세션의 수동 상태 재확인에서 STT_FINAL(length=5)/RELEASED,
condition=PERSISTENT_FATIGUE를 확인했다. 화면은 WARNING(경고 · 피로 지속)으로 전환됐다.
콘텐츠 STOP 요청 SUCCESS와 후속 TTS_DONE 두 차례를 관찰했다.
당시 미디어는 이미 중단되어 있었으므로 재생 중 차단 성공으로 해석하지 않는다.
휴식 검색은 미지원이며 실제 후보 검색·경유지 변경·차량 제어는 수행하지 않았다.
1분 자동 후속 실행을 기다리는 시험과 구분하며 독립 심한 졸음 시험을 위해 음성 연결을 껐다.

## 심한 졸음 시험 준비 중 첫 시도

새 세션 출발 질문의 TTS_DONE→STT_READY→FINAL(length=9)/RELEASED는 수신됐으나
상태 분류 UNCONFIRMED, 모드 명령 분류 SELECT_MUSIC이었다. 원문은 확인하지 않았다.
따라서 NORMAL→모드 질문→로컬 재생 및 심한 졸음 단계까지 도달하지 못했다.
사용자에게 질문별 발화 순서를 확인 요청했으며 심한 졸음 성공으로 기록하지 않는다.

사용자는 첫 정상 응답과 다음 음악 명령을 질문 순서대로 발화했다고 확인했다.
관찰 메타데이터와 사용자 경험의 차이가 있어 발화 순서 오류로 원인을 확정하지 않는다.
복합 흐름 반복 대신 독립 상태 재확인에서 심한 졸음 단일 응답을 먼저 검증한다.
이 시험은 재생 중 차단 검증과 구분한다.

## 심한 졸음 단일 실제 시험

독립 상태 재확인에서 STT_FINAL(length=5)/RELEASED 후 condition=SEVERE를 수신했다.
분류 직후 약 4ms 이내 콘텐츠 STOP 요청/SUCCESS를 관찰했고 약 7.3초 뒤 휴식 안내 TTS_DONE을 확인했다.
화면에서 HIGH_RISK에 해당하는 ‘고위험 의심 · 휴식 권고’를 확인했다.
당시 재생 중 미디어는 없었으므로 활성 음악 중단 성공으로 기록하지 않는다.
이후 별도 상태 질문의 STT_READY/약 10초 후 RELEASED와 응답 미확인도 관찰했다.
따라서 최종 화면의 응답 미확인 설명은 SEVERE 최종 결과와 구분한다.
검색 필요 안내 흐름은 미지원 경계이며 실제 장소 검색·경로 변경·차량 제어를 수행하지 않았다.

## 의도적 침묵 실제 시험과 최종 한계

사용자는 심한 졸음 시험의 휴식 권고를 들었다고 확인했다.
위험 세션을 종료한 새 세션에서 정상·모드 단계를 생략하고 상태 질문 단독으로 침묵 시험을 진행했다.
이는 앞의 정상 확인 후 침묵 계획을 단일 질문으로 분리한 것이며 재생 중 미디어가 없는 시험이다.
TTS_DONE 뒤 STT_REQUESTED/READY, 최종/발화 시작 콜백 없이 약 10초 청취 제한 후
STT_RELEASED와 미확인 안내를 관찰했다. 인접한 두 청취 구간에서 최종 결과 없이 종료됐으며,
화면은 ‘미확인’으로 유지됐다. 추가 질문의 발생 원인은 이 관찰만으로 확정하지 않는다.
명시적 SDK TIMEOUT 오류나 NoResponse 반환을 관찰한 것은 아니다.
실제 관찰로 확인한 범위는 최종 결과 미수신→청취 종료→미확인 유지이며 졸음 확정이 아니다.
명시적 NoResponse의 단계 상승, 권한 거부·서비스 실패 구분은 앞의 52개 자동 테스트 결과로만 보고한다.

| 항목 | 실제 관찰 | 제한 |
|---|---|---|
| 가벼운 피로 | MILD_FATIGUE/CAUTION 및 휴식 권고·환기 미지원 안내 | 첫 입력 누락 원인 미확정 |
| 지속 피로 | PERSISTENT_FATIGUE/WARNING, STOP SUCCESS, 휴식 안내 | 활성 미디어 중단·실제 휴식 검색 아님 |
| 심한 졸음 | SEVERE, 고위험 의심 표시, 즉시 STOP 및 휴식 안내 | 독립 단일 질문; 전체 음악 흐름 재현 미완료 |
| 침묵 | 최종 결과 없이 청취 종료, 미확인 유지 | SDK TIMEOUT/NoResponse 콜백 미관찰 |
| 오류별 무응답 횟수 구분 | Fake·가상 시간·오류 매핑 자동 테스트 52개 성공 | 실제 권한·서비스 장애 유발 안 함 |

기존 코드 변경 없이 검증 문서만 추가했다. 실제 차량 setter·경로 변경·긴급 신고는 실행하지 않았다.
커밋·푸시는 하지 않았다. 이번 관찰만으로 음성 입력의 간헐 실패나 추가 청취 원인이 해결됐다고 주장하지 않는다.

## 후속 수정: 수동 첫 확인 이후 중복 출발 질문

DriveMateSession.conditionCheck는 스케줄러의 출발 질문을 소비하지 않았다.
실제 음성 세션을 출발 확인 대신 상태 다시 확인으로 시작하면, 수동 질문 직후 ticker가
남아 있는 출발 질문을 실행할 수 있었다. NORMAL과 CAUTION 두 가상 시간 회귀 테스트가
수정 전에 모두 실패하여 코드 수준에서 중복 질문을 재현했다.
수동 확인 진입 시 scheduler.takeDue()로 이미 도래한 질문을 병합 소비하도록 수정했다.
미래의 일반 확인과 피로 후속 예약은 유지한다. 공통 계약·B 소유 파일·SDK 호출 변경은 없다.
이 재현은 추가 청취의 가능한 원인을 입증하며, 앞선 모든 실제 발화 누락이나
상태 질문에서 음악 명령이 수신된 원인까지 확정하는 것은 아니다.
수정 APK의 Emulator 실제 발화 재검증은 아직 수행하지 않았다.

수정 후 assembleDebug/testDebugUnitTest 전체 실행: BUILD SUCCESSFUL(57초),
43개 작업 중 8개 실행/35개 up-to-date. XML 합계 449개, 실패 0/오류 0.
수정 전 신규 회귀 2개 실패→수정 후 전체 통과를 확인했다. git diff --check 오류 없음.

## 수정 APK 실제 재검증

수정 debug APK를 adb install -r로 설치(Success)하고 기존 내비 안내는 변경하지 않았다.
앱 재실행 후 실제 내비 관측·차량 읽기·테스트 음 선택·실제 음성을 다시 준비했다.
출발 확인을 먼저 하지 않고 ‘음성 상태 다시 확인’ 한 번으로 시작했다.
TTS_DONE→STT_REQUESTED/READY→STT_FINAL(length=4)/RELEASED→condition=NORMAL을 확인했다.
첫 관찰 20초와 추가 10초 대기 이후에도 마지막 음성 이벤트는 동일한 NORMAL 결과였으며
추가 STT_REQUESTED나 TTS_DONE은 없었다. 화면 음성 IDLE도 확인했다.
따라서 이번 단일 실제 정상 응답 시험에서는 즉시 중복 질문이 재현되지 않았다.
이는 모든 발화 누락이나 복합 음악 흐름의 안정성을 보장하는 결과가 아니다.
원문은 수집하지 않았고, 시험 종료 시 실제 음성 연결을 껐다. 커밋·푸시하지 않았다.
