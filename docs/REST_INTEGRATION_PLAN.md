## 공식 문서 재확인

- Pleos Waypoints: addWaypoint(RequestWaypointInfo), 최대 2개,
  결과는 경유지 콜백으로 확인한다.
  https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/waypoint-settings
- 설치 의존성을 사용하는 PleosNaviBackend.requestWaypoint의 실제 Kotlin 호출과 대조했다.
  기존 빌드가 검증한 시그니처를 유지하며 문서 예제에 맞춰 버전을 변경하지 않는다.
- TMAP POI 통합 검색은 장소·좌표·카테고리 검색이다. 거리순에는 중심 좌표와 반경이 필요하다.
  이 문서만으로 실제 Pleos 경로의 진입 가능성이나 주차를 보증한다고 판단할 수 없다.
  https://tmap-skopenapi.readme.io/reference/장소통합검색
- TMAP 자동차 경로 안내의 rpFlag는 공급자 목적지 진입 속성이다.
  Pleos ID/진입 검증 근거로 자동 변환하지 않는다.
  https://tmap-skopenapi.readme.io/reference/자동차-경로안내

## 구현 순서와 완료 조건

1. **로컬 개발 중계**: 기존 PC 키 보관 방식을 유지하고 합성 위치/경로 fixture로
   요청·취소·오류·키 비노출을 검증한다. 실제 위치·목적지 전송은 별도 명시적 선택으로 분리한다.
   로컬 개발 서버는 운영 배포나 안전 후보 공급 완료가 아니다.
2. **후보 발견과 안전 검증 분리**: POI는 발견 결과로만 취급한다. 공식 시설/좌표계/
   동일 시설/현재 경로 방향·접근·주차 근거가 없는 결과는 VerifiedRestPlace로 승격하지 않는다.
3. **경로 문맥 공급**: 같은 관측 세대/revision의 위치·진행 방향·공급자 경로 근거를
   B 내부 snapshot으로 묶는다. SDK 공개 시그니처·권한 확인 후 읽기만 추가한다.
   현재 RouteProgress의 ETA만으로 근처/진행 방향 판정이 가능하다고 가정하지 않는다.
4. **변경 권한 연결**: 음성 후보 동의만으로 관측 경로를 소유 경로로 바꾸지 않는다.
   실제 변경의 동의 발급·후보 만료·경로 일치·SDK 콜백 완료 기준을 먼저 설계한다.
   isRouting/안내 모드 불일치에 대한 기존 변경 검증을 임의로 완화하지 않는다.
5. **실제 한 경로 시험**: 사용자에게 후보를 안내하고 그 시점의 동의 후에만 실제 경유지를
   요청한다. 빈 결과·거절·취소·만료·경로 변경·늦은 콜백·기존 목적지 보존을 확인한다.
